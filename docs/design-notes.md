# 「引用到输入框」和「添加注释」到底差在哪

两个功能入口长得几乎一样（选中文字 → 浮出按钮），但它们的**目的地**不同，因此成本、时机、可用范围全都不同。

## 一句话对比

| | 引用到输入框 | 添加注释 |
|---|---|---|
| 文字去哪儿 | 你下一条消息里 | 附着在消息上的元数据 |
| 模型看得见吗 | **看得见**（发出去之后） | **看不见** |
| 什么时候发生 | 和下一轮对话同步 | 随时，可异步、可批量 |
| 主要用途 | 「就这段，你再说说」 | 回看、复盘、攒反馈、导出 |
| 代价 | 占上下文 token；改动 prompt 前缀 | 需要存储 + 一个能读回来的界面 |
| DSH 里现成的东西 | 输入机的 `inputActions` | `dsh-message-feedback`（只支持整条助手消息） |

## 为什么「注释」不是「引用」的廉价替代品

### 引用到输入框：便宜的真正原因

它不引入任何新状态。文字只是变成下一条用户消息的一部分，而消息本来就存在。所以：

- 不需要存储格式、不需要迁移、不需要并发控制；
- 不需要「读回来」的界面——你已经把它读回来了（它就摆在输入框里）；
- 语义天然无歧义：模型看到的是一段被 `>` 标出的引文 + 你随后补的问题。

### 注释：贵在必须回答四个问题

只要开始存注释，就绕不开：

1. **锚点是什么？** 整条消息？还是消息内的一个区间？
   - 整条消息：便宜，但表达力约等于「给这条回复打分」，DSH 的 `messageFeedback` 已经是这个粒度。
   - 消息内区间：表达力对，但区间会失效——消息重渲染、上下文压缩、历史替换都会让 offset 漂移。稳妥做法是高位锚点（原文 + 前后文指纹），这是 Hypothes.is 那一类标注系统的核心难点。
2. **存在哪？** DSH 里现成的路子是会话日志事件（`messageFeedback` 就是这么做的：`feedback/message-put` 进 canonical log，带版本号做 CAS）。自己另起一个 store 就等于多了一份真相。
3. **怎么写回模型？** 注释默认不进上下文，那「我标了 12 处，你按这个改」就没法表达——除非再加一个「把注释批量送去对话框」的动作。**这时候它又绕回引用了。**
4. **怎么读回来？** 没有浏览/导出界面的注释等于写日记不翻。这是这个功能真正的成本所在，不是写入，而是读取。

### 结论

- 注释是「**给我自己**」的记录，引用是「**给模型**」的输入。
- 若你的动作永远是「读完这段 → 针对它说点什么」，引用严格更优（少一次复制粘贴、保留出处、不和剪贴板打架）。
- 若你的动作是「先攒着，回头一起处理 / 导出 / 反馈」，那必须做注释，而且要连读取界面一起做。
- 两者不是二选一：合理形态是同一个浮层两个动作，注释面板里每个注释再带一个「送去对话框」。**先做引用**，因为它是这条路径上唯一不需要新状态的那一半。

## 本插件为什么这么做

- **挂载点**：`conversation.input.overlay`（session 作用域）。要写草稿就得拿到会话作用域的东西——`useInput` 是 session 标准 props，而插入引用要 `ctx.sessions.scope(id).conversation`；root 作用域的 `shell.overlay` 两样都拿不到，只能画一个按不动的按钮。
- **不作弊**：插件不去调 shell 私有的 Lexical editor（`ComposerKeyboard` 是包内部面），只走公开草稿动作。
- **不自动发送**：引用块进输入框后由人决定发不发。自动发送会把「引用」变成「替用户提问」，那是另一种产品。
- **出处信息默认不写**：`> 原文` 这种块引用形式本身已经告诉模型这是引文。再加一行「—— 来自助手回复」在模型自己写的内容上只是噪声。（`INCLUDE_PROVENANCE` 常量留了口子。）

## 已经做了的：从「粘文本」改成「引用对象」

第一版点击后是把引用块 `setDraft` 进草稿。它有两个问题：草稿里已有的 `@文件` / `@会话` 芯片会被摊平，而且得到的东西和用户手打无法区分。

现在走引用管线：注册 `ctx.inputTriggers` 源 + `codec`，用 `conversation.input.for(actx).insertReference(ref, span)` 插一枚原子芯片。于是：

- 芯片是一个节点，一个 Backspace 删掉、同一笔撤销；
- 复制草稿摊开成 `> 原文`，发送时由 `codec.serialize` 生产模型文本；
- `ref` 自包含（base64url 内嵌原文），所以解析不依赖插件内存——DSH 对找不到 codec 的定义是**拒绝发送**，不能赌内存。

细节（detect 坐标折算、源名对齐）见 [README 的「怎么做的」](../README.md#怎么做的)。

## 明确不做的：ChatGPT 那种引用卡片

ChatGPT 的引用是一张带**铅笔 / 垃圾桶**的卡片。评估过，不做：

1. **座位不对**。卡片该待的地方是 `conversation.input.attachments`（草稿附件栏）。它是 **single** slot 且标了 `shadows-shipped-ui`——往里加东西等于替换 shell 自己的附件栏，插件会连带接管所有图片/文件的渲染。
2. **按钮是假的**。卡片的删除要"只删这一条"，而公开 API 里没有"从草稿移除某一枚芯片"；`setDraft` 会把草稿整个重写、摊平其它芯片。做出来的卡片要么按钮不工作，要么一按毁掉别的引用。
3. **增量价值有限**：能看全文、多个引用视觉分离。而"是个对象、能单独删、模型文本由 codec 生产"芯片已经全有了。

## 下一步可选项

| 选项 | 价值 | 成本 |
|---|---|---|
| 只读引用卡片（输入框上方镜像显示芯片全文） | 长引用不用去草稿里看 | 低：`conversation.input.overlay` 里按 `occurrences` 渲染；但删除只能回草稿按 Backspace |
| 助手消息动作条上加「整条引用」 | 一键引用整条回复 | 低：已有 `conversation.chat.assistant-actions` 座位 |
| 引用带出处（message id） | 追问时模型知道引的是哪条 | 低：`INCLUDE_PROVENANCE` 常量 + 芯片 `ref` 里加一段 |
| 引用插在光标处而不是末尾 | 更符合直觉 | 中：光标不在公开 props 里，得另找入口 |
| 注释（区间锚点 + 会话日志事件 + 侧栏面板） | 复盘/反馈 | 高：锚点、存储、读取界面三件套 |
| 快捷键（选中后 Cmd+Shift+Q） | 少一次鼠标 | 低 |
